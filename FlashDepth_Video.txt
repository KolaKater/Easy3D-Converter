### 2. 你列的 8 个文件，哪个真的管视频稳定？

### 3. 真正的问题出在哪？分两层

**第一层：FlashDepth 的记忆，现在是“半开半关”的**

在 `flashdepth_model.py` 的 `infer()` 里，它**没有**每次都清空记忆。好消息是：如果你按顺序把视频帧一张一张喂进去，它的记忆是会一直往下传的，深度会比单张稳一点。

坏消息是：`test.py` 从来没有在**新视频开始时**调过一次 `reset_state()`。

所以会发生这种事：你上一个视频最后一帧的记忆，会漏到下一个视频的第一帧里。第一个视频的第一帧也会带着上上个图片的记忆。深度一开始就不准，后面越跑越偏。

打个比方：FlashDepth 的记忆就像一个人看电影，你没告诉他“这是新电影，忘了上一部”，他就一直把上一部的剧情往这一部上套。

**第二层：DA3 L 不适合直接转视频**

你刚才说 `DA3 L`，这个要特别注意：

- **FlashDepth-S / FlashDepth-L**：有上面说的那个 `RNN` 记忆，是专门为视频做的
- **DA3 L**：是单张图片深度模型，**没有记忆**。它每帧都是独立算的，帧和帧之间深度尺度会跳，视频一定闪

所以转视频，必须用 FlashDepth，不能用 DA3 L。DA3 L 只适合转单张照片。

### 4. 要让 Easy3D 真正支持视频，需要改 3 处，不用大改模型

1.  **GUI 加一个视频入口**：选一个 `.mp4`，自动拆成帧，记住顺序，转完再自动拼回视频。现在这一步是你手动在外面做的，顺序一乱，记忆就乱了。
2.  **视频开始时清一次记忆，中间绝不清**：一个视频只在第 0 帧之前调一次 `reset_state()`，第 1 帧到最后一帧都不要清。这样 FlashDepth 才知道“这是一个连续的序列”。
3.  **深度尺度不要每帧单独归一化**：现在 `flashdepth_infer_video.py` 演示里有一句 `(depth - min) / (max - min)`，这个是每帧自己归一化，会把闪烁放大。真正转视频时，整个视频要用同一个尺度。

### V9.0 视频模式，GUI 会自动锁这些，你不用自己记

选了 `.mp4 / .mov / .mkv / .avi / .webm` 之后，日志里会打 `[VIDEO]`，然后自动强制：

**1. MDE 只能 FlashDepth - 这是你说的，肯定的**
- 选了 DA3 / DA2 / MoGe，会自动切回 `FlashDepth-S`
- 原因：只有 FlashDepth 有 RNN 记忆，DA3 / DA2 / MoGe 都是单张图模型，没有记忆，视频一定闪

**2. 别的也要注意的，我都给你锁了：**
- **Seed 强制固定**：Random 会被改成 `681115423`，整段视频同一个种子，每帧随机种子 = 每帧深度都在跳
- **FaceRestore 强制 none**：逐帧 GFPGAN，脸会一帧一样，闪得最明显
- **gen_mode 强制 orig_right**：`both` 是 2 倍扩散，闪的风险翻倍，视频不要用
- **Mode 强制 decoupled_a**：`quality` 模式每帧全量扩散，又慢又闪，视频用 `decoupled_a` 最稳
- **OutputType 强制 parallel**：XD 要多一次 warp，视频上不稳
- **SaveDepth / SaveWarped 强制 OFF**：不然每帧都存一张调试图，几百帧就把盘塞爆
- **LimitToSource 强制 ON**：中途分辨率一跳，深度尺度就跳
- **Chunk / Cooldown 强制 OFF**：这个是最坑的。原来图片版是每 2 张换一个新进程，换进程 = RNN 记忆被清空。视频必须整段视频一个 `test.py` 进程跑完，开头清一次记忆，中间绝不清

**3. 只警告，不锁的：**
- Steps > 25 会警告：时间 = 帧数 x 步数，视频建议 8-15
- Resolution > 1536 会警告：时间 = 帧数 x 分辨率，视频建议 768-1344

### 视频流程现在是这样的

选视频 → 自动拆帧到 `_cache/video_frames/<视频名>/`，按 `frame_000001.jpg` 顺序 → 一个进程跑完 → 输出在输出文件夹 → 你再用 log 里显示的 fps，用 ffmpeg 拼回视频。

有用，而且不只是你这段视频这个分辨率——修的是拼的那套通用逻辑，不是针对某一帧、某一个 `y` 写死的。

### 为什么通用

V9.8 改的是 `generate_novel_view_decoupled.py` 里的 `_stitch_tiles_weighted`，它不写死 `128` 或 `512`，重叠是多少，是现场从 `starts` 反推出来的：

```
overlap = patch - 相邻块起点差
```

所以：

- **A=896**：`patch=512`，`starts=[0,384]`，`overlap=128`，就是你这轮跑的
- **B / C / D**：`patch=896`，`overlap=224`，`starts` 按 `_low` 算，同样走这套
- **2x2 / 3x3**：都是同一套，横向、纵向各算各的重叠，不会拿横向的 `overlap` 去拼纵向
- **单块（不切）**：`overlap=0`，直接原样返回，等于没动，不会多出软化

输出不是方图也没事。GNVD 是先在方图里拼完，再拉回原图尺寸，缝的位置按比例跟着缩放，`feather` 也跟着缩放，所以 `1920x1440` 和别的尺寸都是一样的效果。

### 图片也一样

图片和视频帧，走的是同一个 GNVD 函数，一张图就是一帧。图片用 Decoupled A / B / C / D，只要 `low >= 896`，都会进 GNVD，都会吃到这个修复。

你觉得“画面比之前稳定”，也是同一个原因：每块扩散的 seed 不一样，两块拼的地方以前是 `87%` 跳变，seed 的差值直接露出来，看起来就闪、就抖。现在过渡是 `1%` 一格格爬上去的，seed 的差值被 feather 吃掉了，所以稳了。

### 两种情况不受影响，不用担心

- **不切块的**：比如 `Quality` 单块、`Decoupled` 里 `GNVD` 失败回退老路单块，本来就没有缝，V9.8 不会去软化它
- **老路切块的**：`test.py` 里的 `_stitch_pair`，V9.5 那版已经是重叠区内 `0→1` 的 feather，出口处已经是 `100%` 右块，不会再跳一次，所以老路那条缝本来就没 GNVD 这么硬

一句话：**只要是 GNVD 切块拼的，不管分辨率、图片还是视频，硬线都修了。** 只要确认跑的时候日志里有 `[Easy3D-GNVD]`，用的就是这套。
